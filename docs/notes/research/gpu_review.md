# Movara 局部 GPU 加速

更新时间：2026-10-30。状态：用户已确定局部加速方向，工具与实现待验证。当前仅整理文档，CPU 原型先行；尚未安装、构建或运行 GPU 样例。

## 1. 当前决策

内核先实现 CPU 同步推进与并行决策。GPU 用于有明确收益的计算阶段，避免把整个仿真一次迁到 GPU。若接入成本低且完整阶段提速明显，可以在 CPU 正确性基线建立后提前做小范围试验，无需等待平台所有功能完成。

提高 wgpu 的评估优先级，首先检查跨平台计算、已有 GUI 依赖及数据互操作条件。GPU 加速仍不成为内核运行的必要条件，具体采用以实际收益、构建开销、分发体积和维护难度判断。

用户希望普通分发无需附带大型训练框架，不把 PyTorch/LibTorch 或 JAX 设为基础依赖。Python 研究环境可单独使用这些框架，桌面与无界面基本仿真保持独立。模型权重、GPU 驱动、运行库和应用自身的体积分别记录，当前不承诺固定 MB 数。

已明确不需要内核自动微分、反向传播或训练能力，也不要求仿真可微。计算需求分为一般数值/几何计算与可选模型推理：前者包含运动、坐标变换、搜索、筛选和接触，不限于矩阵运算；后者只执行已训练策略。模型训练和优化留在外部研究环境。

## 2. 分阶段加速的候选

| 计算阶段 | 候选价值 | 需要验证的成本 |
| --- | --- | --- |
| Agent 模型批量推理 | 同模型主体共用权重，批量处理观测 | 模型算子、预处理、记忆、批量大小与 CPU/GPU 传输 |
| 运动更新 | 大批主体执行相近数值计算 | 单次计算量是否足够覆盖调度和回读开销 |
| 邻域与接触候选 | 大量空间查询与包围体筛选 | 空间结构更新、对象尺寸差异、密集区候选增长 |
| 精确接触与区间检测 | 大量同类形状查询 | 分支、形状差异、连续检测与数值验证 |
| 多环境实验 | 多场景组成更大的计算批次 | 动态主体、地图差异、内存占用和任务同步 |
| 场景绘制 | GPU 批量绘制对象 | GUI 后端集成；绘制提速与仿真提速分别计量 |

路线搜索、事件调度、场景编辑与主体生命周期初期保留 CPU 实现。具体计算位置按测量调整，不因为 GPU 可用而迁移所有逻辑。

## 3. 数据与执行边界

CPU 原型采用明确的数值批次，决策、动作、运动和接触分阶段组织。状态按连续集合交付，必要时使用按字段组织的数组；不提前把所有数据强行改成张量，也不为未来后端预建通用运行时。

GPU 接入后每个阶段明确输入、输出、Tick 与数据所有权。设备缓冲区是相应阶段的数据载体，同一世界仍只有一个可提交的状态权威。CPU 与 GPU 副本的有效时刻需要清楚，禁止两边独立修改交通状态。

尽量批量上传、连续计算、按需回读。性能统计包含准备、传输、首次编译、调度、执行、同步和结果回读，不能只比较 GPU kernel 时间。单个实时城市和多环境实验分别测量。

GPU 内部的命令提交与完成等待封装在后端边界，内核 step 仍可保持同步接口。GPU 支持不要求业务全面采用 Rust async。发生已选后端错误时明确报告，不静默切换结果不同的计算路径。

CPU 与 GPU 结果按合理数值容差和事件语义比较，边界接触单独核验。并行归约、随机与浮点差异可能影响长期轨迹，不能提前承诺跨设备逐位一致。保留实际动作与事件用于追溯。

## 4. Rust 候选与 JAX 的关系

以下为官方文档初查，尚未验证本项目适用性。候选各有用途，原型不会全部引入。

| 方案 | 能力与来源 | 对 Movara 的定位 |
| --- | --- | --- |
| wgpu | 原生跨平台 GPU API，提供 ComputePipeline | 优先评估小型自定义计算阶段，通常需编写 WGSL 等 kernel 和管理缓冲区；不提供完整张量训练框架 |
| CubeCL | Rust 计算语言扩展与 JIT/runtime，提供多硬件后端 | 自定义并行 kernel 的候选，可使用 Rust 风格代码；线程组织、内存与同步仍需设计，并非任意 Rust 函数自动 GPU 化 |
| Burn | 张量与深度学习框架，提供多后端及融合能力 | 保留参考，当前不引入；仅在实际模型推理需求合适时评估所需组件，无自动微分需求 |
| Candle | 轻量 Rust ML 框架，包含 CPU 与 GPU 路线 | 模型推理候选，核对算子、目标平台和后端依赖；不默认具备 wgpu 后端 |
| JAX | Python 数组与函数变换体系，包括 JIT、自动微分与批量变换 | Python 研究端可选，当前不作为 Rust 内核分发方案 |

JAX 超出单纯矩阵库范围，其数组计算与函数变换/编译体系需要相应运行环境。Rust 可通过 Python 接入已有 JAX 研究代码；JAX 的官方 FFI用于接入外部操作，也不等于一个可直接替代 JAX Python API 的 Rust 前端。当前未核验成熟 Rust/JAX 直接绑定或导出执行链，暂不依赖它减少分发体积。

当前无需寻找覆盖 JAX 全部能力的 Rust 替代。CPU 使用普通 Rust 与现成数值/几何库，局部 GPU 计算优先比较 wgpu，必要时比较 CubeCL。模型推理待选定模型后核对算子、导出格式、批量状态和后端成本，再选择轻量运行方案；Candle 等仍为候选。Burn 不因提供自动微分而获得优先级。

轻量方案可以避免强制引入 LibTorch，并不表示没有 GPU 驱动、编译、运行库或较大的 Rust 构建依赖。后端特性选择与实际打包结果是体积结论的依据。

## 5. GPUI 与 wgpu 的关系

GPUI Kit 的安装说明说明其使用固定 GPUI snapshot，也有可选 GPUI Fast 后端。具体构建需要固定 Kit、后端与版本，不能从上游 main 直接推断所选发布版本的全部实现。

本轮查阅 Zed 上游：Linux manifest的 Wayland/X11 路径使用 gpui_wgpu；Windows 窗口实现持有 DirectXRenderer。因此“GPUI 所有平台统一使用 wgpu”并不成立。

即使 GUI 和计算都使用 wgpu，版本、adapter、device、queue、缓冲区用途和资源暴露接口仍需匹配，不能假设自动共享显存或零拷贝。若共享需要侵入修改 GUI 内部，先比较独立计算设备与批量数据交付的成本。

内核 GPU 计算可无窗口运行，不依赖 GPUI 的设备生命周期。GUI 已有 GPU 渲染可作为评估 wgpu 的理由，不能作为计算设备共享已可用的证据。

## 6. 后续小试验的验收

先建立同一计算阶段的 CPU 正确结果，选一项完整批次验证 GPU。试验记录小/中/大批次、冷启动与热运行、传输与同步、总耗时、精度、峰值内存和分发依赖。使用目标 Windows 环境，跨平台结论另行确认。

性能收益足以覆盖新增复杂度再采用，低收益则保留 CPU 路径。不为展示 GPU 使用而引入完整后端；当前也不创建 CPU/GPU 双实现或训练设施。
