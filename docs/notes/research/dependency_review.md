# Movara 依赖与技术选型

查阅日期：2026-10-30。状态：官方文档和项目说明初查，未安装、编译、运行或审计候选库。下列能力为来源声明，适用性为待验证判断。具体版本与来源提交在实施时固定。

## 1. 采用原则

优先使用已有库完成解析、曲线、空间查询、碰撞、并行和绑定。先检查项目现有依赖，再引入新依赖。原型选择所需的最少组合，同一责任避免叠加多套实现。

评估同时关注功能覆盖、维护状态、测试样例、跨平台构建、许可证、数据语义与代码可读性。关键库缺口可以影响语言选择，不能因已偏向 Rust 而默认自己补齐所有能力。未检索到合适 Go 候选只表示本轮证据不足，不证明 Go 没有相关库。

完整平台比较以 [SUMO](../../comparisons.md) 为主要交通管理对照，按具体案例评估直接使用、局部复用和自建边界。MetaDrive 与 Waymax 为局部参考，不决定 Movara 整体结构，也不因许可宽松或提供演示而优先采用。

用户所说的“非商用许可证”已澄清为不希望依赖需要购买商业授权的方案，并未要求限制他人商用。具体发布许可证待选择，依赖代码、数据和模型权重分别审查。免费可获取也可能附带使用条件，例如 Waymax 官方声明非商业使用条款；是否直接复用需结合发布目标判断。

## 2. 候选表

| 用途 | 官方来源与已查内容 | 采用前检查 |
| --- | --- | --- |
| 原生桌面 | GPUI Kit 提供桌面组件、表格、Dock 与主题；GPUI 提醒存在 API 破坏性变化 | Windows 与 Linux/macOS 实际支持、输入法、画布绘图、拾取、构建耗时与版本迁移 |
| Go 桌面备选 | MyGo 文档包含原生 GPU UI、自定义绘图、表格和树 | 实际维护与稳定性、复杂画布、跨平台体验；不能直接判定其缺少 Canvas 能力 |
| Python 绑定 | PyO3 与 maturin 提供 Rust/Python 原生扩展构建路线 | 批量数组交互、内存所有权、Python 线程边界、Windows 构建与打包 |
| CPU 并行 | Rayon 支持并行迭代与线程池 | Agent 状态隔离、顺序/并行结果、简单策略下的调度开销 |
| 接触与空间查询 | Parry 为 Rust 二维/三维几何库 | 形状、距离、接触及扫掠查询的具体 API、旋转和步长案例、浮点类型 |
| OpenDRIVE 几何导入 | xodr 描述了折线、车道图与路面网格导入；旧 crate 名为 libopendrive | 当前版本支持的车道类型、信号/物体、路口连接、数值精度与未知结构处理 |
| OpenDRIVE 结构解析 | opendrive 提供 parser/writer 与道路、车道、信号等结构模块，页面标注 1.7.0 对应版本 | 完整几何求值和查询是否需补充、真实导出文件覆盖及 ASAM 派生内容许可 |
| OpenDRIVE 跨语言参考 | C++ libOpenDRIVE 提供解析、几何与路网查询示例，README 声明目标为 1.4 | 新版源地图覆盖、桥接成本和打包；与 Rust 旧名 libopendrive 区分 |

不以“纯 Rust”作为必须条件。若 C++ 等库明显减少地图工程量，先评估绑定与分发成本。也不默认引入完整刚体引擎，交通接触所需的查询能力可以单独采用。

## 3. OpenDRIVE 需要分层核验

ASAM OpenDRIVE 定义静态路网。RoadRunner/CARLA 导出文件的实际版本与子集在接入时记录，不能从文件扩展名推断完整支持。不同来源版本属于外部接口范围，支持边界需要明确。

| 层次 | 需要的证据 |
| --- | --- |
| 结构读取 | 正确读取源版本与字段，明确缺失、未知或不支持内容；检查依赖是否静默丢弃必要数据 |
| 几何 | 直线、圆弧、缓和曲线、宽度、偏移、多车道段；后续高程单独验证 |
| 拓扑 | 车道行驶方向、道路连接、路口连接、分合流和可执行路径 |
| 混合交通 | 人行道、自行车道、过街与等待区域的支持范围，明确额外语义 |
| 信号与规则 | 信号与车道关联、限速、道路标线和允许通行类别 |
| 运行时 | 采样精度、地图边界、最近道路与路径查询、空间索引 |
| 显示与来源 | 内核和画布由同一导入地图派生，保留源道路与车道 ID |

最小样例建议覆盖直路、弯路与简单路口，再抽查真实 CARLA/RoadRunner 地图。先复用可用几何和查询，对缺口逐项选择补充、上游修复或更换库。XML 解析成功不能代替地图验收。

本轮通过 Go/OpenDRIVE/golang/xodr 关键词检索尚未确认可直接采用的 Go 方案。重新比较 Go 时应专门补查，其 XML 标准库存在并不等于已具备道路几何与拓扑能力。

## 4. 模型与推理复用

学习策略候选集中维护在[数据与模型参考](../../design/models.md)。先核对模型的观测、动作、地图和记忆能否连接，再决定继续使用 Python 运行时、导出模型或采用原生推理库。当前不为尚未选择的模型确定 ONNX、LibTorch 或 GPU 依赖。

候选模型存在不等于已有公认、轻量、跨主体和跨地图通用的方案。参数量、权重授权、输入预处理、批量延迟、闭环响应和训练数据范围均需核验。

局部 GPU 方向已确定，CPU 原型先行；wgpu 提高评估优先级，必要时比较 CubeCL。内核不需要自动微分、反向传播或训练，也无需为一般几何计算引入张量框架。推理方案待模型确定后选择，Candle 等保留候选，Burn 当前不引入。训练留在外部研究环境，GPU 驱动、运行库与构建体积另行核验。JAX 和 GPUI 边界见[局部 GPU 加速](../../development.md#cpu-与局部-gpu-计算)。

## 5. 原型决策方式

首选试验组合为 Rust + GPUI Kit + Python 绑定，重要依赖先做最小调用验证。Go 保留为比较路线，Gio/MyGo 等具体备选在需要时评估。Godot 暂不考虑，Bevy 暂不采用。

原型同时评估依赖缺口、冷构建、增量修改、内核局部检查、界面交互及用户对代码的理解。必要时调整模块和依赖；仍不适合则比较语言。当前不承诺任何编译时间或对象规模，也不以维护者承诺替代实际运行。
