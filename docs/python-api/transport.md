# 本机通信

本文定义 Python API 与应用之间的连接边界、消息编码及传输约定。运行流程见[API 运行模型](runtime.md)，请求及结果见[数据与控制](data-and-control.md)。

## 方案与范围

外部客户端采用本机回环地址上的长连接，多个客户端分别连接同一应用，消息统一交给应用协调者处理。GUI 使用进程内 Rust 接口和只读快照，传输编码仅作用于外部连接。

首轮采用裸 TCP 长连接、长度前缀消息和 MessagePack 编码。Rust 与 Python 客户端共用明确的消息结构，应用实现请求、结果、事件及回合的分发。该组合适合项目维护的客户端，依赖和消息边界保持直接。

| 项目 | 约定 |
| --- | --- |
| 监听地址 | 本机 IPv4 回环地址 `127.0.0.1` |
| 端口 | 默认由操作系统分配，应用确认实际端口；显式配置按启动参数处理 |
| 连接 | 每个 Session 维护一条 TCP 双向长连接，承载请求、结果与通知 |
| 消息边界 | 无符号 32 位网络字节序长度前缀，随后为对应字节数的消息体 |
| 编码 | MessagePack，结构化消息使用有明确字段名的映射 |
| 状态交付 | 批量发送对象基础状态，Python 解码为本地只读包装对象 |
| 版本 | 握手校验明确的协议版本，版本不匹配返回错误 |

TCP 为本机与跨机器连接提供统一基础，后续远程接入沿用相同的消息和回合语义。首轮服务范围限定在本机。远程监听、认证、加密及部署按对应阶段单独设计。

MessagePack 通过现成库编解码。Rust 侧采用 Serde 与相应 MessagePack 实现，Python 侧采用 msgpack。具体依赖版本和运行时集成在技术验证后固定。

连接和字节读写复用成熟的 socket 与 I/O 能力，MessagePack 使用现成编解码库。应用维护长度分包、领域消息、请求身份及回合调度。

### 传输协议与并发模型

传输采用 TCP，同步或异步 I/O 按应用集成需要确定。Tokio 可以用于通信适配，其采用与内核接口分别决定。内核不要求 Tokio 运行时。

仿真推进、Agent 决策接口和运动计算保持同步语义。采用异步网络运行时时，其范围限制在应用通信适配中，通过消息队列与同步仿真工作线程交换请求和结果。GUI 采用自身事件循环，进程内调用沿用统一协调入口。

同步 I/O 同样需要组织连接的并发读写、消息唤醒和关闭。具体线程或任务模型根据客户端规模及应用集成验证确定，界面线程与仿真计算保持清楚的职责边界。

TCP 提供可靠有序的字节流，应用通过长度前缀定义完整消息。实现覆盖部分读写、消息长度校验、未完成消息的断开处理，以及请求身份、超时、队列与仿真回合管理。

首轮采用一套消息编码，状态对象保持完整基础信息。共享内存、按列传输、压缩和其他优化按测量结果安排。

## 多实例与启动就绪

应用完成监听与初始化后发布实例身份、endpoint 和协议版本。GUI 提供查看或复制连接信息的入口，`connect` 使用明确的 endpoint 连接已有实例。

`launch` 为子进程安排独立的就绪回报通道，接收实际 endpoint 后建立普通 API 连接，再完成订阅与查询登记。就绪报告和连接握手都校验实例身份，场景通过后续加载建立。

就绪通道的 Windows 实现结合进程启动验证确定，GUI 模式沿用无额外控制台窗口的启动要求。启动和连接等待采用明确的墙钟期限，失败返回所处阶段及已知实例信息。

## 消息边界与结构

接收方完整读取长度前缀，再读取对应长度的消息体并解码 MessagePack。长度前缀只表示后续消息体的字节数，发送和接收分别处理部分读写。实现设置有界的消息长度与队列，具体上限通过批量数据验证确定。

| 消息内容 | 用途 |
| --- | --- |
| 消息类型 | 区分握手、请求、接收回执、执行结果、控制回合、事件与状态通知 |
| 请求身份 | 关联调用与结果，主动通知按其自身事件或回合身份组织 |
| 运行身份 | 校验目标实验与运行上下文，实例操作按对应范围表达 |
| 回合与版本 | 关联固定输入阶段、控制提交及数据所属版本 |
| 负载 | 有类型的命令、动作、查询结果、事件或错误 |

应用为连接来源和命令接收顺序分配可信身份。解码后继续执行相应领域校验，传输成功与命令实际生效分别确认。

对象、事件与命令按批次传输。实现可以将同一批次的运行、时间和版本放在共同元数据中，Python 包装对象保持完整的访问语义。

## 调度与错误交付

消息接收按请求及回合身份分发，生命周期通知独立于仿真 Tick。网络 I/O 和用户计算期间，应用继续接收消息并处理允许的查询。

无法解码、超出消息上限或协议版本错误返回具体协议错误并结束相应连接。队列容量和超时具有明确上限，无法继续交付时报告连接失败。控制连接失败和观察连接失败沿用各自的运行语义。

调用方查询已经超时的请求时继续使用原请求身份。命令重试由调用方明确发起，应用保持原执行事实和结果。

## 验证要求

| 场景 | 检查内容 |
| --- | --- |
| Windows GUI/headless 启动 | 就绪回报、连接建立与模式一致性 |
| 多实例与多客户端 | endpoint、实例身份、命令来源与回合完整性 |
| 消息分片与连续消息 | 长度前缀及消息体的部分读取、完整分包、连续消息和异常断开 |
| 查询与控制交错 | 固定版本查询、单步与回调提交、生命周期通知 |
| 较大批量状态 | 编解码、传输、Python 对象构造、内存和交互延迟 |
| 关闭、断线与超时 | 预期关闭、结果不确定、必需控制方失败及诊断 |

协议作为首轮实现基础，技术验证确定具体 I/O 集成、依赖版本、就绪通道和消息上限。性能评价覆盖协议处理、编解码、传输与对象构造。
