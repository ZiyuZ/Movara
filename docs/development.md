# 开发指南

本指南面向 Movara 贡献者，说明工程组织、开发规范、技术选型与文档维护要求。

## 工程组织

| 模块 | 目录 | 职责 |
| --- | --- | --- |
| 内核 | `crates/movara-core` | 世界模型、仿真运行与记录 |
| 应用 | `crates/movara-app` | GUI、headless 与外部 API 入口 |
| Python API 库 | `crates/movara-python` | 实例连接、应用启动与 Python 操作接口 |

三个模块在同一仓库中按职责组织。Cargo 工作区管理 Rust 包的版本与 edition，Python 包采用自己的项目配置。原生扩展和其他内部组件按实际接口与性能需要引入。

应用以单个可执行文件提供 GUI 和 headless 模式，内核在应用进程内运行。Python API 库通过应用接口访问相应仿真实例。系统边界见[核心设计](design/core.md)，程序调用见[Python API 设计](python-api/README.md)。

## 实施准备

文档整体审查完成后，按[技术验证计划](design/validation.md)安排验证程序与依赖。验证结论用于固定具体版本、数值参数和首轮任务，设计中的候选能力按实际结果说明。

### 目录与配置

| 内容 | 目录约定 |
| --- | --- |
| Rust 内核与相应行为测试 | `crates/movara-core/src`、`crates/movara-core/tests` |
| 应用、GUI 与通信接入 | `crates/movara-app` |
| Python API、测试与实验示例 | `crates/movara-python/src`、`crates/movara-python/tests`、`crates/movara-python/examples` |
| 可分发地图与场景样例 | `assets/maps`、`assets/scenes` |
| 本地运行输出与详细验证记录 | 已忽略的 `.local/` |

目录按实际交付内容创建。场景配置首轮采用 JSON，包含明确的格式版本，加载时校验引用、字段与取值范围。OpenDRIVE 地图保持源格式，场景通过相对路径及明确的资源身份引用地图。样例采用仓库可分发的自足资源。

依赖版本通过验证后写入对应项目清单与锁文件。应用运行配置、协议版本与场景格式版本分别表达。正式接口说明与代码类型同步维护。

### 第一轮任务顺序

1. 建立可独立运行的地图、运动、界面和通信验证入口，取得相应采用结论。
2. 实现最小场景、主体中心状态与同步逻辑步，验证直接控制及状态查询。
3. 接入道路查询、运动约束与区间接触，形成安全通过与事故停驶案例。
4. 接入应用协调与 Python 单步，验证批量对象、命令结果及运行生命周期。
5. 接入基础 GUI 与 Python 参考策略，完成相同场景的不同入口验收。
6. 根据阶段范围补充事件回调、注册变更、轨迹及记录能力。

各任务以可执行案例和明确结果作为完成条件。实现顺序可以根据依赖验证调整，首轮范围以[技术原型方案](design/prototype.md)为准。

统一开发入口由根目录 `justfile` 维护。Python 的 Ruff、ty 与测试入口在验证工程建立时补齐，命令使用 Windows 工具链；Markdown 检查继续使用 `just rumdl`。

## 开发命令

在仓库根目录通过 `just` 执行统一的检查和构建命令。Rust 使用 Windows MSVC 工具链，编译产物目录由 Cargo 配置指定。

| 命令 | 用途 |
| --- | --- |
| `just fmt` | 格式化 Rust 代码 |
| `just build` | 构建 Cargo 工作区 |
| `just check` | 检查 Rust 格式、编译和 Clippy 诊断 |
| `just test` | 执行 Rust 单元、集成与文档测试 |
| `just rumdl` | 格式化并检查 Markdown |

工具链和已采用依赖在验证后固定版本。应用工程提交 `Cargo.lock`，依赖更新时同步维护锁文件。Python API 库的构建、检查与依赖由其项目配置管理。

## 开发规范

### 命名与注释

标识符、文件名和配置字段使用英文，遵循对应语言的命名惯例。文档与解释性注释使用中文，标准名称和外部接口术语保持其原有拼写。

代码按职责组织，优先采用清楚的结构体、枚举和普通函数。抽象应服务当前需求，模块与文件在规模影响理解时拆分。

功能设计从使用场景与调用流程明确操作、数据、时序和错误语义，再映射到应用与内核职责。Python API 可以作为实验与自动化需求的主要入口，运动、接触和信息边界仍通过独立案例验证。

注释说明设计理由、单位、边界条件和特殊算法。公开接口说明输入、输出、错误与副作用。Python 接口提供类型标注。

### 错误与配置

可预期失败通过明确的错误类型返回，包含对象、操作和原因等上下文。断言用于内部不变量。外部输入失败通过错误返回处理。`panic` 和 `unwrap` 不用于处理可预期的输入错误。

配置默认值具有明确含义并写入文档。加载时校验未知字段、取值范围和相互约束，错误应指出具体位置或字段。具体配置格式在接口设计中确定。

### 格式与依赖

文本统一使用 UTF-8 和 LF。编辑器与 Git 通过根目录配置维护一致的文本格式。Rust 使用 rustfmt 和 Clippy。Python 使用 uv 管理项目与依赖，Ruff 负责检查和格式化，ty 负责类型检查。工具配置由对应项目维护，日常命令通过 `just` 提供统一入口。

依赖按实际用途引入，采用前检查能力、许可、维护与分发成本。已采用依赖通过清单和锁文件管理，工具链版本在验证后固定。

### 测试与验证

测试优先验证可观察行为，覆盖运动、接触、时间、信息边界与恢复等关键约束。缺陷修复尽量增加能够复现问题的回归测试。

验证范围与变更影响匹配。文档和格式修改执行相应检查，行为修改运行相关测试。覆盖率数字不作为形式化目标。验证结果需要区分格式、编译、运行与领域行为。

### Git 与协作

每次提交围绕一个完整目的，变更范围保持集中。提交信息采用 `类型: 中文说明`，例如 `docs: 整理核心执行语义`。常用类型包括 `feat`、`fix`、`refactor`、`test`、`docs` 和 `chore`。

采用简单分支流程，独立工作需要隔离时建立短期分支。提交和推送按明确指令执行，日常修改默认保留在工作区。

已确定范围内自主完成修改与必要验证。范围、核心语义或重大选型变化先行讨论。工作记录保存有意义的进展、结论、验证与遗留问题。

## 版本与设计演进

项目采用版本号描述能力与接口边界。1.0 之前允许持续调整或重构设计、接口与内部格式，相关调用方、样例、测试和文档同步更新。内部格式采用直接演进，高成本资产按需要执行一次性迁移。

1.0 表示一个经过定义和验收的版本边界。后续仍可进行重大设计调整，不兼容的公开变更通过提升主版本号表达，并说明影响与迁移方式。新增兼容功能和修复分别使用次版本号与修订号。

各版本的能力、接口与数据要求由对应版本文档说明。长期旧版本兼容层不作为默认维护承诺。

## 平台与技术路线

Windows 原生环境是主开发与优先验收平台，Rust 使用 MSVC 工具链。跨平台支持按各平台的实际构建、运行和交互结果说明。

内核与应用采用 Rust，桌面优先评估 GPUI Kit。Python API 库封装应用提供的操作接口，内部语言与传输实现按实际需求选择。技术选型同时考虑功能覆盖、增量构建、分发成本和代码维护。

Go 保留为重要依赖或维护体验不满足要求时的比较方案。当前方案不采用 Godot、Bevy 或完整游戏引擎。

## 依赖选择

优先复用成熟库完成地图解析、曲线、空间查询、接触、并行与通信。每项职责采用必要的最小依赖组合。

| 领域 | 技术候选 | 采用条件 |
| --- | --- | --- |
| 桌面组件与画布 | GPUI Kit / GPUI | 目标平台、输入法、绘图、拾取、构建成本与版本维护满足要求 |
| Python API 实现 | Python 与必要的原生或通信组件 | 接口语义、实例管理、批量数据、错误返回和构建分发 |
| CPU 并行 | Rayon | 主体状态隔离，顺序与并行结果符合确定性约定 |
| 几何与接触 | Parry | 形状、距离、旋转、扫掠与接触查询覆盖目标场景 |
| OpenDRIVE 几何 | xodr | 几何、路口、车道与源文件覆盖符合导入要求 |
| OpenDRIVE 结构 | opendrive | 结构解析、版本处理和几何补充成本明确 |
| 跨语言地图方案 | C++ libOpenDRIVE | 地图能力收益能够覆盖绑定、构建与分发成本 |
| Go 桌面备选 | Gio / MyGo | 在重新比较语言时验证画布、维护与跨平台体验 |

选型应检查维护状态、测试覆盖、许可证和数据语义。具体版本与来源提交在采用时固定。地图与几何库可以通过跨语言绑定接入。

核心依赖采用免费可用的方案。需要购买商业授权的方案不进入核心依赖。项目发布许可证、依赖代码、数据和模型权重的使用条件分别审查。

## 地图导入验收

地图支持范围包含源版本、结构、几何、拓扑与运行查询。XML 解析成功仅表示结构读取阶段完成。

| 层次 | 验收内容 |
| --- | --- |
| 结构 | 源版本与字段读取，缺失、未知及不支持内容的明确处理 |
| 几何 | 直线、圆弧、缓和曲线、宽度、偏移与多车道段 |
| 拓扑 | 行驶方向、道路与路口连接、分合流及可执行路径 |
| 混合交通 | 人行道、自行车道、过街区、等待区与附加语义 |
| 规则 | 信号与车道关联、限速、标线和通行类别 |
| 查询 | 采样精度、地图边界、邻近道路、路径与空间索引 |
| 显示 | 绘图数据与运行地图一致，源道路和车道 ID 可追溯 |

地图样例先覆盖直路、弯路与简单路口，再检查实际导出文件。缺口可以通过补充实现、上游修复或更换依赖解决。高程支持单独验证。

## CPU 与局部 GPU 计算

CPU 提供基础数值、几何与策略执行。GPU 按完整计算阶段的收益采用，优先评估批量推理、运动更新、邻域筛选和接触查询。路线搜索、事件、编辑和生命周期初期由 CPU 处理。

计算按输入、输出、Tick 和所有权组织批次。状态可以采用连续集合或按字段组织的数组。一般几何与搜索保持适合其算法的数据结构。

GPU 缓冲区表示某一阶段的数据副本，其有效时刻和提交关系需要明确。世界状态由内核统一提交。GPU 提交与等待封装在计算后端，外部 `step` 保持同步。

| 方案 | 用途 | 主要接入要求 |
| --- | --- | --- |
| wgpu | 优先评估的局部 GPU 计算接口 | 计算着色器、缓冲区、调度与数据传输 |
| CubeCL | 自定义并行计算的备选 | 线程组织、内存、同步与目标硬件支持 |
| Candle | 按模型需求评估的推理候选 | 算子、模型格式、批量状态与目标平台 |
| Burn | 初始方案之外的框架候选 | 模型需求、所需组件、后端与分发成本 |
| JAX | Python 研究环境中的计算工具 | 独立运行环境及与平台的输入输出边界 |

内核提供一般数值、几何计算和可选策略推理。自动微分、反向传播与模型训练属于外部研究环境。PyTorch/LibTorch 和 JAX 不作为应用基础运行依赖。

推理库在模型确定后选择，检查算子、导出格式、预处理、记忆与批量延迟。采用轻量框架后仍需检查驱动、运行库、构建依赖和应用体积。

### 渲染设备互操作

GUI 渲染与内核计算分别设计。GPUI 的实际后端取决于平台和所选版本，需固定框架及后端组合。

共享 GPU 资源要求版本、适配器、设备、队列、用途和接口匹配。独立计算设备与批量数据交付也是可评估方案。设备共享条件不得从绘图库名称推断。

### 性能与数值评价

GPU 评价覆盖数据准备、传输、首次编译、调度、执行、同步和回读。冷启动、热运行、小中大批次、峰值内存和分发体积分别记录。单城市实时仿真与多环境批量实验分别测量。

CPU 与 GPU 按数值容差和事件语义比较，接触边界单独检查。浮点、归约与随机执行差异可能改变长期轨迹。跨设备逐位一致性不作为预设保证。

采用后端的错误应明确报告。禁止通过静默切换计算路径掩盖失败。GPU 在完整阶段收益能够覆盖维护成本后采用，低收益场景继续使用显式选择的 CPU 方案。

## 工程质量

内核独立构建与测试，应用调用内核，Python API 库通过应用接口工作。局部逻辑修改应具有相应的局部检查入口。

实现优先采用普通结构体、枚举、连续集合和稳定 ID。共享可变状态、复杂抽象与框架按实际需求引入。Rust 默认使用安全代码，底层绑定等特殊机制需要明确用途。

验证涵盖运动、接触、时间、信息隔离、命令原子性和恢复完整性。确定性例子比较顺序、并行和不同遍历顺序。显示刷新变化应保持仿真结果一致。

构建评价包括冷构建、增量修改、内核检查和桌面启动。代码审阅应能定位世界、动作与逻辑步，并完成简单行为修改。性能评价还应覆盖查询、决策、运动、接触、快照和画布。

内部格式变化采用直接迁移或明确失效。高成本资产可以执行一次性迁移。错误暴露后应修复其原因。兼容层、静默降级、无限重试和多层恢复不得用于掩盖错误。

## 文档站

文档站采用 VitePress，正文保留在正式文档目录，站点配置、主题、构建脚本和依赖清单集中在 `.github/docs-site/`。平台文档、Python API 与应用界面使用独立导航，新增页面时同步维护该目录下 `.vitepress/config.mjs` 的分区导航。

站点依赖通过目录内的 `package.json` 与 `bun.lock` 管理，Bun 统一负责依赖安装、准备脚本和 VitePress 运行。日常只需编辑 Markdown 和图片，安装与完整构建由 GitHub Actions 执行。

Workflow 将站点工程复制到 `.local/docs-site/project/` 后安装和构建，汇集正文时保持仓库相对路径，跨模块链接与 SVG 引用继续共用同一份 Markdown。源码副本、依赖、缓存和产物均放在 `.local/docs-site/`。本地验证也使用这一隔离目录。任务 prompt、本地笔记和归档目录不进入站点。

`.github/workflows/docs.yml` 在相关 PR 中构建站点，在 `main` 的相关变更或手动触发后发布。GitHub 仓库的 Settings → Pages → Build and deployment → Source 需要选择 GitHub Actions。首次发布后可以从 workflow 的部署结果进入网站。

构建时通过 `MOVARA_REPOSITORY` 指定仓库根目录，在隔离工程内执行 `bun run docs:build`，输出为 `.local/docs-site/dist/`。完整构建检查与发布结果由 Actions 提供，Markdown 格式继续通过 `just rumdl` 检查。站点使用浏览器内搜索，中文索引和查询采用相同的分词规则。

## 文档维护

文档按完整主题组织，相近的小节优先在同一专题内维护。内容增长到影响阅读与维护时，可以按职责拆分。目录按相关领域分组，专题数量继续增长时再建立必要的子层级，避免在单个目录堆积零散页面。拆分与目录重构同步维护内容归属和导航。

具有独立目标、范围和验收条件的方案单独成文，路线图保留阶段目标与方案入口。原型的具体安排集中在[技术原型方案](design/prototype.md)。移动现有章节优先使用命令行脚本保留原文，再修改结构、衔接和引用。

正式文档面向第三方用户和贡献者。`docs/` 顶层维护需求、开发指南、同类工具对比、路线图和筹备计划，具体设计集中在 `docs/design/` 的领域专题中。根目录 README 提供稳定介绍与导航。应用专属的 GUI 工作区、视觉与组件规范集中在 [`crates/movara-app/docs/`](../crates/movara-app/docs/README.md)，系统职责和跨模块交互继续在桌面界面设计中维护。

Python API 的使用与接口约定集中在 `docs/python-api/`。关键流程和跨接口规则由手写文档维护，参数、返回值、异常与局部示例以代码 docstring 为主要来源，后续参考文档由签名、类型与 docstring 生成。

正文图示采用独立绘制的 SVG，按内容设计布局、分组与标注，保持统一的学术文档风格。对应的 Mermaid 源码以折叠的文本代码块保留在图示附近，修改图示时同步维护其语义。空间几何示意可直接使用 SVG。流程图节点中的文字作为整体水平、垂直居中，标题与副说明共同排布。图外标注和泳道标题按阅读关系对齐，页脚说明按内容需要设置。

章节标题使用领域概念，正文说明行为、接口、条件与设计理由。设计方案、候选技术与已交付能力分别表述。表格列名应指明具体内容，例如“职责”“接口”“采用条件”和“评价指标”。

采用正面陈述。概念对照和范围限制分别成句，必要的否定使用独立句。术语在首次使用时说明，并在各文档中保持一致。

句中出现否定或转折时，应检查表达是否可以拆分。避免“是 A；而不是非 A”“不是 A；而是非 A”这类对照结构，减少“应当 A；而不是 B”“采用 A；无需 B”“A；不假定 B”等写法。

正式文档维护模块职责、接口语义、使用方法和开发规范，任务级进度集中在 TODO。详细实现状态、环境信息、构建结果、调研与工作过程记录在已忽略的 `.local/notes/`。本地记录不纳入 Git，正式文档保持自足。日常维护跳过用户管理的 `archive/`。

修改文档时通读所属章节及相关引用，检查语义、结构、能力状态和重要信息覆盖。新增标题、移动章节或合并文件后，同步更新根目录导航与内部链接。

全面审查覆盖相关正式文档的读者定位、章节结构、术语、措辞与技术约束。关键词搜索和格式工具提供辅助，正文仍需逐篇审阅。

Markdown 格式化与检查统一执行：

