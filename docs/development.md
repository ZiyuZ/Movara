# 开发指南

本指南面向 Movara 贡献者，说明开发规范、技术选型、计算后端与文档维护要求。当前已建立基础 Rust 工作区，仿真、桌面和 Python 绑定仍处于设计阶段。

## 工程结构与命令

根目录 Cargo 工作区统一管理版本与 Rust edition。`crates/movara-core` 是内核库的初始构建单元，当前仅提供工程骨架。GUI、CLI 和 Python 绑定的构建单元随接口设计与依赖验证确定。

应用交付采用单个可执行文件，运行时以默认 GUI 或 `--headless` 选择启动模式。内核与 GUI 分别组织，应用在进程内调用内核。构建单元按代码职责确定，产品入口遵循[启动模式设计](design/gui.md#应用与启动模式)。

在仓库根目录执行以下命令。Rust 命令使用已安装的 Windows MSVC 工具链，编译产物位置由 Cargo 配置确定。

| 命令 | 用途 |
| --- | --- |
| `just fmt` | 格式化 Rust 代码 |
| `just build` | 构建 Rust 工作区 |
| `just check` | 检查 Rust 格式、编译和 Clippy 诊断 |
| `just test` | 执行 Rust 单元、集成与文档测试 |
| `just rumdl` | 格式化并检查 Markdown |

当前使用本机已安装的 Windows stable 工具链。工具链的具体版本固定方案随技术验证确定。应用工程提交 `Cargo.lock`，更新依赖时同步记录锁文件。

## 开发规范

### 命名与注释

标识符、文件名和配置字段使用英文，遵循对应语言的命名惯例。文档与解释性注释使用中文，标准名称和外部接口术语保持其原有拼写。

代码按职责组织，优先采用清楚的结构体、枚举和普通函数。抽象应服务当前需求，模块与文件在规模影响理解时拆分。

注释说明设计理由、单位、边界条件和特殊算法。公开接口说明输入、输出、错误与副作用。Python 接口提供类型标注。

### 错误与配置

可预期失败通过明确的错误类型返回，包含对象、操作和原因等上下文。断言用于内部不变量。外部输入失败通过错误返回处理。`panic` 和 `unwrap` 不用于处理可预期的输入错误。

配置默认值具有明确含义并写入文档。加载时校验未知字段、取值范围和相互约束，错误应指出具体位置或字段。具体配置格式在接口设计中确定。

### 格式与依赖

文本统一使用 UTF-8 和 LF。编辑器与 Git 通过根目录配置维护一致的文本格式。Rust 使用 rustfmt 和 Clippy，Python 引入时确定对应工具。日常命令通过 `just` 提供统一入口。

依赖按实际用途引入，采用前检查能力、许可、维护与分发成本。已采用依赖通过清单和锁文件管理，工具链版本在验证后固定。

### 测试与验证

测试优先验证可观察行为，覆盖运动、接触、时间、信息边界与恢复等关键约束。缺陷修复尽量增加能够复现问题的回归测试。

验证范围与变更影响匹配。文档和格式修改执行相应检查，行为修改运行相关测试。覆盖率数字不作为形式化目标。验证结果需要区分格式、编译、运行与领域行为。

### Git 与协作

每次提交围绕一个完整目的，变更范围保持集中。提交信息采用 `类型: 中文说明`，例如 `docs: 整理核心执行语义`。常用类型包括 `feat`、`fix`、`refactor`、`test`、`docs` 和 `chore`。

当前采用简单分支流程，独立工作需要隔离时建立短期分支。提交和推送按明确指令执行，日常修改默认保留在工作区。

已确定范围内自主完成修改与必要验证。范围、核心语义或重大选型变化先行讨论。工作记录保存有意义的进展、结论、验证与遗留问题。

## 版本与设计演进

当前版本从 `0.1.0` 起步。1.0 之前允许持续调整或重构设计、接口与内部格式，相关调用方、样例、测试和文档同步更新。内部格式采用直接演进，高成本资产按需要执行一次性迁移。

1.0 表示一个经过定义和验收的版本边界。后续仍可进行重大设计调整，不兼容的公开变更通过提升主版本号表达，并说明影响与迁移方式。新增兼容功能和修复分别使用次版本号与修订号。

各版本的能力、接口与数据要求由对应版本文档说明。长期旧版本兼容层不作为默认维护承诺。

## 平台与技术路线

Windows 原生环境是主开发与优先验收平台，Rust 使用 MSVC 工具链。跨平台支持按各平台的实际构建、运行和交互结果说明。

初始技术组合优先评估 Rust 内核、GPUI Kit 桌面与 PyO3/maturin 绑定。语言与框架选择同时考虑功能覆盖、增量构建、分发成本和代码维护。

Go 保留为重要依赖或维护体验不满足要求时的比较方案。当前方案不采用 Godot、Bevy 或完整游戏引擎。

## 依赖选择

优先复用成熟库完成地图解析、曲线、空间查询、接触、并行与绑定。每项职责采用必要的最小依赖组合。

| 领域 | 技术候选 | 采用条件 |
| --- | --- | --- |
| 桌面组件与画布 | GPUI Kit / GPUI | 目标平台、输入法、绘图、拾取、构建成本与版本维护满足要求 |
| Python 绑定 | PyO3 / maturin | 明确批量数据、内存所有权、线程边界与 Windows 打包方式 |
| CPU 并行 | Rayon | 主体状态隔离，顺序与并行结果符合确定性约定 |
| 几何与接触 | Parry | 形状、距离、旋转、扫掠与接触查询覆盖目标场景 |
| OpenDRIVE 几何 | xodr | 几何、路口、车道与源文件覆盖符合导入要求 |
| OpenDRIVE 结构 | opendrive | 结构解析、版本处理和几何补充成本明确 |
| 跨语言地图方案 | C++ libOpenDRIVE | 地图能力收益能够覆盖绑定、构建与分发成本 |
| Go 桌面备选 | Gio / MyGo | 在重新比较语言时验证画布、维护与跨平台体验 |

选型应检查维护状态、测试覆盖、许可证和数据语义。具体版本与来源提交在采用时固定。地图与几何库可以通过跨语言绑定接入。

核心依赖采用免费可用的方案。需要购买商业授权的方案不进入核心依赖。项目发布许可证、依赖代码、数据和模型权重的使用条件分别审查。

## 地图导入验收

地图支持范围包含源版本、结构、几何、拓扑与运行查询。XML 解析成功仅表示结构读取阶段完成。

| 层次 | 验收内容 |
| --- | --- |
| 结构 | 源版本与字段读取，缺失、未知及不支持内容的明确处理 |
| 几何 | 直线、圆弧、缓和曲线、宽度、偏移与多车道段 |
| 拓扑 | 行驶方向、道路与路口连接、分合流及可执行路径 |
| 混合交通 | 人行道、自行车道、过街区、等待区与附加语义 |
| 规则 | 信号与车道关联、限速、标线和通行类别 |
| 查询 | 采样精度、地图边界、邻近道路、路径与空间索引 |
| 显示 | 绘图数据与运行地图一致，源道路和车道 ID 可追溯 |

地图样例先覆盖直路、弯路与简单路口，再检查实际导出文件。缺口可以通过补充实现、上游修复或更换依赖解决。高程支持单独验证。

## CPU 与局部 GPU 计算

CPU 提供基础数值、几何与策略执行。GPU 按完整计算阶段的收益采用，优先评估批量推理、运动更新、邻域筛选和接触查询。路线搜索、事件、编辑和生命周期初期由 CPU 处理。

计算按输入、输出、Tick 和所有权组织批次。状态可以采用连续集合或按字段组织的数组。一般几何与搜索保持适合其算法的数据结构。

GPU 缓冲区表示某一阶段的数据副本，其有效时刻和提交关系需要明确。世界状态由内核统一提交。GPU 提交与等待封装在计算后端，外部 `step` 保持同步。

| 方案 | 用途 | 主要接入要求 |
| --- | --- | --- |
| wgpu | 优先评估的局部 GPU 计算接口 | 计算着色器、缓冲区、调度与数据传输 |
| CubeCL | 自定义并行计算的备选 | 线程组织、内存、同步与目标硬件支持 |
| Candle | 按模型需求评估的推理候选 | 算子、模型格式、批量状态与目标平台 |
| Burn | 初始方案之外的框架候选 | 模型需求、所需组件、后端与分发成本 |
| JAX | Python 研究环境中的计算工具 | 独立运行环境及与平台的输入输出边界 |

内核提供一般数值、几何计算和可选策略推理。自动微分、反向传播与模型训练属于外部研究环境。PyTorch/LibTorch 和 JAX 不作为应用基础运行依赖。

推理库在模型确定后选择，检查算子、导出格式、预处理、记忆与批量延迟。采用轻量框架后仍需检查驱动、运行库、构建依赖和应用体积。

### 渲染设备互操作

GUI 渲染与内核计算分别设计。GPUI 的实际后端取决于平台和所选版本，需固定框架及后端组合。

共享 GPU 资源要求版本、适配器、设备、队列、用途和接口匹配。独立计算设备与批量数据交付也是可评估方案。设备共享条件不得从绘图库名称推断。

### 性能与数值评价

GPU 评价覆盖数据准备、传输、首次编译、调度、执行、同步和回读。冷启动、热运行、小中大批次、峰值内存和分发体积分别记录。单城市实时仿真与多环境批量实验分别测量。

CPU 与 GPU 按数值容差和事件语义比较，接触边界单独检查。浮点、归约与随机执行差异可能改变长期轨迹。跨设备逐位一致性不作为预设保证。

采用后端的错误应明确报告。禁止通过静默切换计算路径掩盖失败。GPU 在完整阶段收益能够覆盖维护成本后采用，低收益场景继续使用显式选择的 CPU 方案。

## 工程质量

内核独立构建与测试，桌面和 Python 绑定分别依赖内核。局部逻辑修改应具有相应的局部检查入口。

实现优先采用普通结构体、枚举、连续集合和稳定 ID。共享可变状态、复杂抽象与框架按实际需求引入。Rust 默认使用安全代码，底层绑定等特殊机制需要明确用途。

验证涵盖运动、接触、时间、信息隔离、命令原子性和恢复完整性。确定性例子比较顺序、并行和不同遍历顺序。显示刷新变化应保持仿真结果一致。

构建评价包括冷构建、增量修改、内核检查和桌面启动。代码审阅应能定位世界、动作与逻辑步，并完成简单行为修改。性能评价还应覆盖查询、决策、运动、接触、快照和画布。

内部格式变化采用直接迁移或明确失效。高成本资产可以执行一次性迁移。错误暴露后应修复其原因。兼容层、静默降级、无限重试和多层恢复不得用于掩盖错误。

## 文档维护

正式文档面向第三方用户和贡献者。`docs/` 顶层维护需求、开发指南、同类工具对比、路线图和筹备计划，应用设计集中在 `docs/design/` 的核心、GUI 与模型专题中。根目录 README 提供稳定介绍与导航。

章节标题使用领域概念，正文说明行为、接口、条件与设计理由。设计方案、候选技术与已交付能力分别表述。表格列名应指明具体内容，例如“职责”“接口”“采用条件”和“评价指标”。

采用正面陈述。概念对照和范围限制分别成句，必要的否定使用独立句。术语在首次使用时说明，并在各文档中保持一致。

句中出现否定或转折时，应检查表达是否可以拆分。避免“是 A；而不是非 A”“不是 A；而是非 A”这类对照结构，减少“应当 A；而不是 B”“采用 A；无需 B”“A；不假定 B”等写法。

会话背景、个人环境、阅读过程和调查流水记录在 `docs/notes/`。该目录按工作记录、调研与审查分类维护。正式文档独立表达有效结论，其内部链接指向当前正式文档。历史资料与内部笔记不作为阅读前提。日常维护跳过用户管理的 `archive/`。

修改文档时通读所属章节及相关引用，检查语义、结构、能力状态和重要信息覆盖。新增标题、移动章节或合并文件后，同步更新根目录导航与内部链接。

全面审查覆盖相关正式文档的读者定位、章节结构、术语、措辞与技术约束。关键词搜索和格式工具提供辅助，正文仍需逐篇审阅。

Markdown 格式化与检查统一执行：

```sh
just rumdl
```

格式工具检查结构与样式。内容审阅还需确认表达适合目标读者，技术语义与交付状态准确。
